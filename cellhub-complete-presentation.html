CellHub

A complete cellphone repair shop management system — customers, repair jobs, payments, inventory & reports in one place.

Node.js + Express SQLite (better-sqlite3) JWT Authentication Render Deployment Vanilla JS Frontend

What It Does

👥 Customers

Add, view, search customers. Required: name + phone. Optional: email, address. Delete blocked if they have jobs or payments.

🔧 Repair Jobs

Track device model, issue, job type, price. Status workflow: Pending → In Progress → Completed → Released. Linked to a customer.

💰 Payments

Record payments for jobs (partial/full) or walk-in product sales. Methods: Cash, GCash, Maya, Card. Validates balance, prevents overpay.

📦 Inventory

Products with category, price, stock, reorder level. Low-stock alerts on dashboard. Stock auto-decrements on sale.

📊 Reports

Sales by date range: totals, by payment method, by day, top 5 products, outstanding balances. Print-friendly.

🌤 Weather

Current weather for Lucena (or any city). 5-min cache, 30 req/min limit. Shows temp, humidity, condition + shop tip.

How to explain this in 30 seconds

"CellHub replaces paper notebooks for a cellphone repair shop." Instead of writing customer names, repair details, and payments in a notebook, the shop owner uses this web app. It runs on a $0 Render free tier, uses a simple SQLite database, and has zero build step — just plain JavaScript. The stack is intentionally boring so it's easy to maintain and deploy.

Why this architecture?

Monolith, not microservices. One Express app handles everything — auth, API, static file serving, business logic. This is the right choice for a small app: simple to deploy, simple to debug, simple to understand. No network calls between services, no distributed tracing needed.

Why SQLite? Zero configuration, file-based, perfect for a single shop with one database. better-sqlite3 is synchronous (no async/await needed) and faster than async drivers for local files.

No ORM. Raw SQL with parameterized queries. More control, fewer dependencies, easier to audit. The schema is small enough that an ORM would add complexity without benefit.

Stateless auth. JWT tokens mean the server doesn't store sessions. If we ever needed to scale horizontally (multiple server instances), we could — though SQLite wouldn't support that.

Key insight: nullable foreign keys

A payment row has either job_id or product_id (never both, enforced in code). Job payment: customer pays for a repair → has customer_id + job_id. Walk-in sale: customer buys a case → has customer_id + product_id + quantity. Anonymous sale: walk-in buys charger, no customer record → only product_id. One table handles all three cases.

Special endpoints explained

/jobs pagination: ?page=1&limit=10&sort=date_received&order=desc&status=Pending&job_type=Screen%20Replacement. Frontend uses this for the jobs table.

/payments atomic logic: Job payment validates balance (can't overpay). Product sale uses db.transaction() — stock decrement + payment insert happen together or not at all. Prevents overselling.

/reports/sales: One endpoint returns everything: totals, by payment method, daily breakdown, top 5 products, outstanding balance, full item list. Frontend just renders it.

Weather caching: In-memory Map per city, 5-minute TTL. Rate limited to 30 requests/minute. WeatherAPI free tier has strict limits.

Key Features & Design Decisions

🔐 JWT Authentication

  • Stateless — no server sessions
  • 1-hour expiry, stored in localStorage
  • bcrypt cost 10 for password hashing
  • Login rate-limited (10 per 15 min)
  • All mutating endpoints protected
Why JWT over sessions?

No server-side session store needed. Token contains user ID, email, role. Works across multiple server instances (if we ever scale). Simple but secure enough for this scale. Downside: can't revoke individual tokens without a blocklist — acceptable for a small app.

🛡 Referential Integrity

  • Foreign keys ON in SQLite (PRAGMA foreign_keys=ON)
  • Deletes blocked in code (409 error)
  • Clear messages: "Delete jobs first"
  • No cascade — explicit is safer
Why block instead of cascade?

Cascade deletes are scary — one mistake wipes history. Blocking forces you to think: "Do I really want to delete this customer who has 5 jobs and 3 payments?" Data integrity > convenience. The 409 response tells you exactly what to clean up first.

💉 SQL Injection Safe

  • All queries use ? placeholders
  • better-sqlite3 prepared statements
  • Zero string concatenation in SQL
The #1 security win

db.prepare('SELECT * FROM users WHERE email = ?').get(email) — the ? is never executed as SQL. Impossible to inject. This is the single most important security practice in the codebase. No ORM needed; prepared statements are built into the driver.

⚡ Atomic Transactions

  • Product sales: stock−1 + payment insert
  • db.transaction(() => { ... })
  • Both succeed or both roll back
Why transactions matter

Without transactions, you could decrement stock but crash before recording payment = phantom sale (stock down, no money recorded). Transaction = all or nothing. SQLite transactions are fast and synchronous.

🌱 Auto Seed Data

  • On empty DB: 8 customers, 8 jobs, 8 products, 10 payments
  • Demo admin from env vars
  • Survives redeploys on Render
Seed data = demo-ready

Every deploy on Render wipes the DB. Seed data means the live demo always works with realistic data. Demo admin means I can always log in. This is a workaround for ephemeral storage — not a substitute for persistent data in production.

✅ Input Validation

  • Every field checked: type, range, enum, required
  • 400 with specific message
  • Email regex, price ≥ 0, status enum
Validation philosophy

Validate early, reject fast, tell the user exactly what's wrong. if (!Number.isInteger(customer_id)) return 400 — no generic "invalid input". Frontend shows the exact error message. Also prevents bad data from reaching the database.

🌤 Smart Caching

  • Weather endpoint caches 5 min per city
  • In-memory Map (simple, fast)
  • Rate-limited to 30 requests/minute
Why cache weather?

WeatherAPI free tier = 1M calls/month. 30 req/min limit prevents abuse. 5-min cache means 10 users checking weather = 1 API call. In-memory Map is fine for a single server instance; would need Redis for horizontal scaling.

📦 Error Handling

  • Centralized middleware at bottom of server.js
  • 400 bad JSON, 409 FK conflict, 401 auth, 500 server
  • Consistent format: {error: "message"}
Error handling pattern

All errors funnel through two middleware functions. entity.parse.failed catches malformed JSON. SQLITE_CONSTRAINT_FOREIGNKEY catches FK violations (though we check in code first). console.error logs server errors; user sees generic "Something went wrong".

Mobile-first tables: On desktop they're normal tables. On mobile they scroll horizontally in a wrapper. No column hiding, no data loss.

Deployment & The Critical Caveat

✅ What Works on Render Free Tier

  • Node.js 22, Express, SQLite all run fine
  • Auto-deploys from GitHub on push
  • Health check at /health (Render pings this)
  • Env vars for secrets (JWT_SECRET, WEATHER_KEY, DEMO_EMAIL/PASSWORD)
  • Demo admin recreated on every deploy
  • Seed data inserted on every deploy

⚠️ The Problem: Ephemeral Storage

Render's free tier uses ephemeral storage. The cellhub.db file is deleted on every redeploy, restart, or when the app spins down after inactivity.

What survives: Seed data (re-inserted on start), Demo admin (recreated from env vars)

What is LOST: Any real customers, jobs, payments, products you manually add

What "ephemeral storage" means in plain English

Think of it like a container that gets thrown away and recreated fresh every time. The code and env vars persist (they're in Git), but the database file does not. On Render free tier, your app runs in a container that can be stopped/restarted at any time. When it restarts, the filesystem is reset to what's in your Git repo — which doesn't include cellhub.db (it's in .gitignore).

Fix Options (pick one)

Option 1: Render PostgreSQL (Free) ⭐ Recommended

  • Persistent, managed Postgres — also free
  • Change better-sqlite3 → pg
  • Minor SQL syntax changes (? → $1, $2)
  • Data survives forever
  • ~2-3 hours of work

Option 2: Render Paid ($7/mo)

  • Persistent disk for SQLite file
  • No code changes needed
  • But costs money monthly

Option 3: Railway / Fly.io

  • Free persistent volumes
  • More config work
  • Good free tiers

Option 4: Supabase / Neon / PlanetScale

  • External managed Postgres/MySQL
  • Free tiers available
  • Connection pooling included

For a class project or demo: current setup is fine. For a real shop taking money: you must migrate to persistent database.

Testing approach

Integration tests over unit tests: Tests hit real HTTP endpoints against a running server. More realistic, catches real bugs. Test database: Uses a separate test DB file so tests don't pollute dev data. No mocking: Tests the actual code paths. Fast enough: Node's built-in runner is quick; no transpilation needed.
